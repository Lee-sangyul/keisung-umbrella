# ☂️ Keisung Umbrella — v1.0 운영 준비 후보 (미출시)

학교 공용 우산 대여·반납 관리 프로젝트. FastAPI + SQLite 서버 기반이며, **GitHub Pages 단독으로는 작동하지 않습니다.**

## 화면 구성

- `/` — **16:9 터치 키오스크**, 대여/반납 선택 → 학년·반·번호 숫자 타일 선택 → QR 스캔/ID 입력 → 최종 확인 → 완료 (테이블링의 현장 등록식 단계형 UX 참고)
- `/admin` — 별도 관리자 로그인 및 관리 대시보드 (학생별 검색, 우산 상태 관리, 이력)
- `/admin/print` — **관리자 전용 QR 인쇄 센터:** 단일/일괄 인쇄, 우산 ID 검색·상태 필터, A4/Letter, 가로/세로, 열·행·여백·QR 크기·제목·ID 표시·테두리 설정
- `/api/...` — 서버에서 기록 검증·저장

## Codespaces 실행 (Linux)

```bash
git pull
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

그다음 `.env`를 열어 **ADMIN_PASSWORD를 실제 강력한 비밀번호로 변경**하세요. (최소 12자, 저장소에 커밋하지 마세요.)

```dotenv
ADMIN_USERNAME=admin
ADMIN_PASSWORD=본인이_직접_정한_강력한_비밀번호
APP_ORIGIN=
SECURE_COOKIES=true
DATA_DIR=./data
```

`APP_ORIGIN`은 기본적으로 비워둡니다. Codespaces 프록시가 원래 Host를 전달하지 않아 로그인에서 **"요청 출처가 올바르지 않습니다"**가 뜬다면, Codespaces **PORTS** 탭에 있는 **실제 HTTPS 주소**를 그대로 넣으세요(끝에 `/` 없이).

```dotenv
APP_ORIGIN=https://YOUR-CODESPACE-8000.app.github.dev
```

서버 실행:

```bash
uvicorn server:app --host 0.0.0.0 --port 8000 --reload
```

Codespaces Ports에서 **8000 포트를 Private**으로 유지하고 Forwarded Address를 열어보세요. 메인 주소는 학생 키오스크, `/admin`은 관리자 로그인 화면입니다.

**v0.4 변경:** `python-dotenv`가 `.env` 값을 기존 셸 `export` 값보다 우선 적용합니다. 아래 명령은 이전 설정을 정리하고 싶을 때만 선택적으로 실행하세요.

```bash
unset ADMIN_USERNAME ADMIN_PASSWORD APP_ORIGIN SECURE_COOKIES DATA_DIR
```

이제 서버 재시작 시 `.env` 관리자 계정 정보가 SQLite에 반영되고 이전 세션은 만료됩니다. `ADMIN_PASSWORD`는 **실제 비밀번호**여야 하고 `CHANGE_ME` 예시값은 사용할 수 없습니다. 서버 재시작 후 `/admin`에 `.env`의 `ADMIN_USERNAME` 및 `ADMIN_PASSWORD`와 정확히 같은 값을 입력하세요.

### HTTP 401/403에 관하여

- `GET /api/admin/me`의 **401**은 로그인 전 정상 동작입니다.
- 로그인 **403**은 브라우저 Origin과 실제 공개 Host/설정된 `APP_ORIGIN`이 맞지 않는 경우입니다.
- 로그인 **401**은 비밀번호 불일치 등 인증 실패입니다.
- 로그인 성공 뒤 브라우저에서 쿠키가 유지되지 않으면 HTTPS 주소와 `SECURE_COOKIES`를 확인하세요.

## 우산 상태와 이력

- `UMB-0001`부터 등록 순서대로 고유 ID 증가. 삭제·ID 재사용 기능 없음.
- 우산당 대여 1건, 학생당 동시 대여 1개. SQLite 트랜잭션으로 동시 요청 검증.
- 반납에는 학년·반·번호 일치 및 발급된 학생 PIN 인증이 필요합니다. 학년·반·번호 자체만으로는 본인 인증이 아닙니다.
- 관리자 상태: `LOST`(분실), `DAMAGED`(파손), `DISPOSED`(폐기). 분실·파손 복구 가능, 폐기 복구 불가.
- 이벤트는 SQLite DB에 추가되며 관리자 `/api/admin/export`에서 JSON 백업 가능합니다.
- 브라우저 QR 스캔은 BarcodeDetector 지원 및 카메라 HTTPS 권한이 필요합니다. 지원하지 않으면 ID 수동 입력.

## 데이터베이스(DB) 초기화 — 테스트 환경 전용

> **주의:** 초기화하면 우산 목록·대여 및 반납 기록·패널티·월별 정책·관리자 세션이 새 DB에서 초기화됩니다. ID도 `UMB-0001`부터 다시 발급되므로 **기존 QR 라벨을 붙인 운영 중 우산이 있다면 실행하지 마세요.**
>
> **실제 운영 DB에는 사용 금지.** 초기화는 테스트 환경에서만 진행하세요.

### 실행 방법 (Codespaces / Linux / Windows)

1. **Uvicorn 서버와 DB에 접근하는 모든 프로그램을 완전히 종료**합니다.
2. 프로젝트 폴더에서 아래 명령을 실행합니다.

```bash
python reset_db.py
```

3. 표시되는 DB 경로를 확인하고, 정말 초기화하려면 **`RESET`** 을 입력합니다. 다른 입력은 취소됩니다.
4. SQLite 온라인 백업 API로 **일관된 `umbrellas.db` 스냅샷**을 만들고 무결성을 검사한 뒤, 기존 원본은 같은 백업 폴더의 `umbrellas.db.original`로 이동합니다. `-wal`/`-shm` 파일은 존재를 가정하지 않습니다. 연결이 남아 있거나 WAL/SHM 파일이 남으면 초기화를 중단합니다.
5. 서버를 다시 실행합니다.

```bash
uvicorn server:app --host 0.0.0.0 --port 8000 --reload
```

서버 재시작 시 `init_db()`가 새 DB·관리자 계정·기본 월 10회 정책을 다시 생성합니다. `/admin`에 재로그인하여 확인하세요.

**복구:** Uvicorn과 모든 DB 연결을 완전히 종료하고 새 테스트 DB를 다른 곳에 보관한 뒤, 검증된 백업 폴더의 `umbrellas.db` 파일을 원래 `DATA_DIR/umbrellas.db`로 복사하세요. 이 파일은 SQLite가 만든 **일관된 스냅샷**이므로 별도 WAL/SHM 파일을 복구할 필요가 없습니다. 백업 폴더의 `umbrellas.db.original`도 보관됩니다. 복구 전에는 새 DB의 `-wal`/`-shm` 파일이 남아 있지 않은지 확인하세요. 백업 파일은 공개 GitHub에 올리지 마세요.

**참고:** 월별 대여 제한은 매월 1일(한국 시간) 자동으로 새달 기준 계산됩니다. 월별 횟수 초기화만을 위해 DB 전체를 리셋할 필요는 없습니다.

## 배포 전 필수 검토

- 학생 학년/반/번호는 개인정보가 될 수 있으므로 실제 운영 전 학교 승인·보호조치·보존 기간이 필요합니다.
- 학생은 6자리 PIN 인증이 필요하지만, PIN 공유나 엿보기는 막지 못합니다. **학교 실사용 전 강화된 학생 인증 및 교직원 확인 절차가 필요합니다.**
- 관리자 로그인 시도 제한, 계정 관리/비밀번호 변경, 운영 로그 모니터링 등은 추가 필요합니다.
- 외부 서버는 HTTPS 필수, `SECURE_COOKIES=true` 사용. `DATA_DIR`는 영구 저장 볼륨이어야 합니다.
- `.env`, SQLite DB, JSON 백업을 공개 GitHub에 업로드하지 마세요.
- 기존 브라우저 `localStorage` v0.1 기록은 서버로 자동 마이그레이션하지 않습니다.

## 로그인 401 오류 해결 순서

1. `git pull`, `pip install -r requirements.txt` 실행
2. `.env`를 열어 `ADMIN_USERNAME`, `ADMIN_PASSWORD`를 실제 값으로 수정 (예시 `CHANGE_ME...` 사용 금지)
3. Uvicorn을 완전히 종료(Ctrl+C)한 뒤 다시 시작
4. Codespaces의 **Ports** 탭에서 포트 8000의 HTTPS 주소 접속 → `/admin`
5. 로그인 필드에 `.env`의 값과 **완전히 같은** ID/비밀번호 입력. 앞뒤 공백이나 기존에 브라우저가 저장한 암호 자동완성 확인

`/api/admin/me` 요청의 로그인 전 401은 정상이고, `POST /api/admin/login`의 401은 계정/비밀번호 불일치입니다. 로그인 요청에서 403이면 `APP_ORIGIN`과 Codespaces 접속 URL을 확인하세요.

**보안:** Codespaces 포트는 Private으로 유지하고 비밀번호, `.env`, DB를 공유하거나 커밋하지 마세요. 학생 PIN 최초 등록은 교사 승인 없이 즉시 처리되므로, 실제 학교 도입 전 신원 확인과 보안·개인정보 정책 검토가 필수입니다.


## 우산 일괄 등록 (v1.0)

관리자 로그인 후 **`/admin` → 우산 관리 → 우산 일괄 등록**에서 수량을 입력해 한 번에 여러 우산을 등록할 수 있습니다.

- **1~500개** 사이의 정수만 허용하며 관리자 로그인과 CSRF 검사가 필요합니다.
- `POST /api/admin/umbrellas/batch`는 SQLite 트랜잭션으로 전체 등록을 처리합니다. 등록 중 오류가 발생하면 이번 요청의 등록 작업을 모두 롤백합니다.
- 새 우산은 항상 `AVAILABLE` 상태로 등록되고 `UMB-0001` 형식의 고유 ID가 연속 발급됩니다. 기존 ID는 재사용하지 않습니다.
- 등록 내역은 우산별 `REGISTER` 이벤트에 `일괄 등록` 사유로 기록됩니다.
- 성공하면 등록된 수량과 첫 번째·마지막 ID가 표시됩니다. **방금 등록한 QR만 일괄 인쇄** 버튼으로 인쇄 센터에 이동하면 신규 우산만 자동 선택됩니다.
- 잘못 등록된 우산도 ID 삭제·재사용은 지원하지 않습니다. 등록 수량을 꼭 확인하세요.

## QR 라벨 인쇄 (v0.8)

관리자 로그인 후 `/admin/print`로 이동하세요. `/admin`의 우산 관리 목록에서 `QR 인쇄`를 누르면 해당 우산만 선택됩니다. `QR 일괄 인쇄`로 여러 우산을 선택하거나 상태별 필터·검색으로 일괄 선택할 수 있습니다.

- `segno` 패키지가 서버에서 실제 스캔 가능한 QR SVG를 생성합니다. QR에는 **우산 ID만** 담고 학생 정보는 포함되지 않습니다.
- 인쇄 설정: A4/Letter, 세로/가로, 열(1~4), 행(2~8), QR 크기(20~50mm), 여백(5~20mm), 제목/ID/절취선 표시 여부.
- QR 생성 API `POST /api/admin/qr-labels`는 **관리자 세션 및 CSRF 검증**을 거치고 등록된 우산 ID만 처리합니다. 인쇄 UI는 요청을 200개씩 나눠 처리하며 최대 1,000개까지 지원합니다.
- 인쇄 창에서 미리보기 확인 후 **인쇄 시작**을 클릭합니다. 프린터 배율 100%, 브라우저 머리글/바닥글 끄기 권장. 최초 인쇄는 시험 출력 후 실제로 QR 인식되는지 확인하세요.
- 요청한 크기가 라벨 안에 들어가지 않으면 인쇄를 막고 설정을 조정하라는 메시지를 표시합니다. 실제 라벨지 위치 정합성은 프린터/용지에 따라 달라질 수 있습니다.

기존 서버를 종료한 뒤 `git pull origin main && pip install -r requirements.txt` 후 Uvicorn을 다시 시작해야 `segno` 의존성이 적용됩니다. 

## QR 스캔 (브라우저 호환)

학생용 `/` → 대여 또는 반납 → 학생 정보 선택 → **QR 스캔 시작**을 클릭하세요. 브라우저의 카메라 접근을 허용하면 QR 스캔 팝업에서 인식할 수 있고, 성공하면 우산 ID (`UMB-0001` 형식)가 자동 입력됩니다.

- 브라우저에서 `BarcodeDetector`를 지원하면 우선 사용하며, 없거나 오류가 발생하면 저장소에 포함된 `assets/jsQR.js`로 QR을 판독합니다. 외부 CDN 없이 동작합니다.
- 카메라를 사용할 수 없다면 우산 ID를 수동 입력할 수 있습니다. **QR 사진 업로드 및 이미지 파일 인식 기능은 제공하지 않습니다.**
- 스마트폰은 HTTPS에서 카메라 권한을 허용해야 합니다. `http://localhost` 등 허용되는 로컬 개발 환경 외의 일반 HTTP 주소에서는 카메라를 열 수 없습니다.
- 저장소 내 `jsQR`은 Apache-2.0 라이선스의 오픈소스 라이브러리이며 `assets/jsQR-LICENSE.txt`를 함께 제공합니다.
- 스캔은 QR에 담긴 우산 ID 형식만 검증합니다. 학생 PIN 인증과 대여 가능 여부는 서버 API에서 처리됩니다.


## 학교 우산 재고 실사 모드 (v1.4)

관리자 `/admin` → **재고 실사** 메뉴에서 학교 전체 또는 **보관 위치별** 우산 수량을 확인할 수 있습니다. **안전 알림이나 자동 분실·파손 처리는 포함하지 않습니다.**

### 시작하기

1. **우산 관리** 메뉴에서 우산을 등록합니다. 등록되어 있지 않은 우산은 실사할 수 없습니다.
2. 보관 위치별 실사를 하려면 **재고 실사 → 보관 위치 일괄 지정**에서 시작·끝 우산 번호(예: `UMB-0001` ~ `UMB-0500`)와 위치 이름(예: `본관 1층`)을 입력합니다. 한 번에 **최대 500개**를 지정할 수 있으며, 반복하면 2,000개 이상의 우산에도 적용됩니다. 기존 우산의 기본 위치는 `미지정`입니다.
3. **새 재고 실사 시작**에서 실사 이름과 범위를 선택해 시작합니다. `학교 전체` 또는 실제 지정한 보관 위치를 선택할 수 있습니다.
4. 실사 중에는 **우산 ID 직접 입력**, **여러 ID(최대 500개) 일괄 입력**, **QR 카메라 스캔**으로 실물을 확인합니다. QR은 HTTPS/localhost의 카메라 권한이 필요하며, 지원 가능한 브라우저에서는 BarcodeDetector 또는 포함된 jsQR로 판독합니다.
5. 실사 세션에서 **대상 수, 확인 수, 미확인 수, 대상 외 확인 수**를 확인하고 **결과 CSV**를 내려받습니다.
6. **실사 완료**를 누르면 세션이 읽기 전용이 됩니다. 결과는 DB 및 관리자 JSON 백업에 남습니다.

### 정확성 및 보안 관련 주의

- **실사 시작 시점**에 `AVAILABLE`(대여 가능) 또는 `DAMAGED`(파손) 상태인 우산만 확인 대상으로 *스냅샷* 저장합니다. 대여 중(`BORROWED`), 분실(`LOST`), 폐기(`DISPOSED`) 상태는 예상 수량에서 제외합니다.
- 실사 시작 이후 우산의 상태나 위치가 바뀌어도 기존 대상 목록은 자동으로 바뀌지 않습니다. 실사 진행 중 정상 대여가 발생하거나 우산이 이동한 경우 **미확인으로 남을 수 있으니 실제 기록을 확인하세요.** 필요하면 새 세션으로 다시 실사합니다.
- 대상 이외의 우산을 스캔하면 *대상 외 확인*으로 남으며, 미등록 우산은 별도 안내합니다. 중복 확인도 별도로 표시합니다.
- 실사와 보관 위치 지정은 **관리자 세션 및 CSRF 검사**가 필요합니다. 학생용 공개 키오스크에서는 실사 목록과 위치 정보를 가져올 수 없습니다.
- **실사 결과만으로 우산 상태를 변경하거나 학생에게 패널티를 부과하지 않습니다.** 실사 미확인과 실제 분실은 다르며, 관리자가 대여 기록과 현장 위치를 확인한 후 별도 처리해야 합니다.
- 세션 조회·CSV는 관리자 전용입니다. CSV는 우산 ID와 점검 결과 위주로 내보내며 학생 식별자를 넣지 않습니다. CSV·전체 JSON 백업 파일은 비공개로 보관해야 합니다.
- 실사 기능은 센서 없이 사용 가능합니다. 모바일 카메라 스캔은 **실제 사용하는 브라우저·기종에서 추가 현장 검증**이 필요합니다.

## 학년도 승급 및 영구 학생 ID (v1.8)

2026학년도 `5-2-14` 학생이 2027학년도 `6-1-7`이 되어도 **같은 사람으로 연결**하기 위해, 학년·반·번호와 별도로 `STU-...` 형식의 변하지 않는 학생 UID를 관리합니다. 실제 학생 이름·생년월일을 저장하지 않으며, **UID와 현재 학년·반·번호의 연결 관계를 관리자 전용 DB에 저장**합니다.

- **유지:** 학생이 등록한 PIN 해시, 대여·반납 이력, 대여 기한, 월간 대여 횟수, 추가 허용 횟수, 패널티 및 취소 기록, 현재 미반납 우산
- **변경:** 새 학년도 학년·반·번호. 기존 이벤트·대여 로그에 적힌 과거 학년·반·번호는 당시 상태 그대로 보존
- **번호 재사용:** 예전 `5-2-14`를 다음 해 다른 학생이 쓰더라도 기존 학생의 PIN/패널티/우산을 가져오지 않습니다. 새 학생은 새 UID와 PIN을 사용합니다.
- **교직원:** `STAFF:` 계정 및 교직원 대여 기록은 학생 학년도 변경의 대상이 아닙니다.

### 연말·신학기 승급 절차

1. 먼저 **운영 DB(`data/umbrellas.db`)와 함께 WAL/SHM 파일을 일관된 방식으로 백업**하거나 SQLite 온라인 백업을 만듭니다. 관리자 JSON 백업에는 PIN 해시가 없어 **JSON만으로는 PIN 복구가 불가능**합니다.
2. 관리자 `/admin` → **학년도·승급 관리**를 엽니다. 현재 학년도 명단을 `TSV`로 다운로드하고, 학교의 **공식 신학기 반 편성 명단**과 학생별로 대조합니다.
3. `new_student_id` 열에 새 학년·반·번호를 입력합니다. 6학년 졸업 예정자는 `GRADUATE`, 전출자는 `LEAVE`를 입력합니다. 기존 학생 **한 명도 누락하면 안 됩니다**. 입학생/새로 전학 오는 학생은 새 학년도 적용 후 키오스크 최초 PIN 등록 또는 관리자 발급으로 신규 UID를 만들 수 있습니다.
4. 모든 ID 열을 **텍스트 형식**으로 열어야 합니다(Excel이 `5-2-14`를 날짜로 바꿀 수 있음). 완성한 TSV 또는 CSV를 관리자 화면에 가져온 뒤 **미리보기**를 실행합니다.
5. 미리보기는 **중복 학급, 누락 학생, 승급 학년 오류, 미반납 우산이 있는 졸업·전출 대상자**를 검사합니다. 안전한 정상 승급은 한 학년 위로만 허용됩니다. 유급·복학 같은 예외는 개별 배정 보정으로 처리합니다.
6. 공식 명단 대조와 DB 백업을 체크한 뒤 **최종 적용**하면 학년도가 한 번에 변경됩니다. 잘못된 처리나 중간 실패는 SQLite 트랜잭션으로 전부 되돌립니다.
7. 승인 후에는 **개별 배정 보정**에서 영구 UID를 확인하고 잘못된 반·번호 또는 복학 배정을 수정할 수 있습니다. 이미 다른 학생이 배정된 번호는 거절하며 담당 교사의 신원 확인과 사유(5자 이상)를 기록합니다.

**주의:** 이 프로그램은 공식 학생명부와 자동으로 연결되어 있지 않습니다. **이름 또는 번호만으로 동명이인/동일인 여부를 추론하지 않습니다.** 학교 관리자와 담당 교사가 공식 자료로 UID–새 학급 연결을 검토해야 합니다. 과거 이력만 존재하는 오래된 번호도 최초 DB 이관 시 명단에 포함될 수 있으며, 이 경우 `LEAVE`로 명시적으로 정리해야 합니다. 다른 학생의 UID에 잘못 연결하면 기존 PIN과 이력까지 연결되므로 최종 적용은 반드시 사전 검토하세요.

학년도는 서버에서 무단으로 매년 자동 변경되지 않습니다. **관리자가 명시적으로 다음 학년도로 적용**해야 하며, 졸업·전출 학생은 기존 PIN과 기록을 보존하지만 새 학년도 반 배정이 없으므로 키오스크 이용은 차단됩니다. 미반납 대여가 있으면 졸업·전출 적용 자체를 차단합니다.

기존 `student_pins`의 PIN 해시는 신규 `student_credentials` 테이블로 복사하여 영구 UID에 연결합니다. 기존 테이블은 이전 기록 복구·마이그레이션 호환성을 위해 남겨두고, **새 인증에는 사용하지 않습니다**. 서버 재시작과 중복 이관에도 기존 UID 및 PIN을 유지합니다.

### 관련 API

`GET /api/admin/academic-year`: 학년도와 UID 명단 조회.
`POST /api/admin/academic-year/preview`: 학급 배정 미리보기·검증.

## 학생 PIN 첫 설정 (교사 승인 기능 제거)

학생용 키오스크 `/`에서 학년·반·번호를 선택하면 최초 이용 시 직접 **숫자 6자리 PIN**을 두 번 입력합니다. 등록 직후 대여·반납에서 사용할 수 있습니다.

- 학생 PIN은 `scrypt` + 고유 salt로 해시 보관하며 원문은 DB에 저장하지 않습니다.
- 기존 PIN 등록자는 설정 화면을 건너뛰며, 기존 PIN을 그대로 사용합니다.
- 동일 숫자 반복 또는 `123456` 같은 너무 쉬운 PIN은 차단됩니다. PIN 5회 연속 실패 시 15분간 잠금 상태가 됩니다.
- 최초 등록된 PIN을 학생이 임의로 덮어쓸 수 없습니다. PIN을 잊으면 관리자 `/admin` → **학생·패널티 관리**에서 담당 교사가 신원을 확인한 뒤 재발급합니다.
- **이전에 등록 승인 대기·반려 상태였던 PIN도 승인 단계 제거 후 원래 PIN으로 사용할 수 있습니다.** 기존 SQLite 데이터와 PIN 해시는 유지됩니다. 과거 승인 관련 테이블이 DB에 남아 있어도 새 프로그램은 사용하지 않습니다.
- **주의:** 학년·반·번호만으로 학생 신원을 확인할 수 없어, 다른 학생이 먼저 등록하여 PIN을 선점할 수 있습니다. 실제 학교 운영 전 별도 신원 확인 및 보안 정책을 마련하세요.

## 교직원 전용 대여 (v1.6)

**학생 PIN 및 대여 흐름은 그대로 유지합니다.** 교직원은 학교에서 발급한 별도의 계정으로 학생과 동일한 **`/` 통합 키오스크**에서 공용 우산을 대여·반납합니다. 계정 이름과 ID는 관리자만 조회할 수 있습니다.

### 관리자: 교직원 계정 발급

1. `/admin` → **교직원 대여 관리**에서 교직원 ID(영문/숫자/하이픈/밑줄 3~20자), 이름 또는 표시명(2~50자)을 입력합니다.
2. 실제 교직원 신원을 확인하고 체크한 뒤 발급합니다. 서버에서 **임의의 6자리 PIN**을 생성해 **그 순간에만** 관리자에게 보여 줍니다. PIN은 안전한 방법으로 해당 교직원 본인에게 전달해야 합니다.
3. 관리자 메뉴에서 PIN 재발급 또는 계정 활성·비활성 변경이 가능합니다. PIN 재발급 시 기존 PIN은 무효화됩니다.
4. 비활성 계정은 새 대여가 불가능하지만, 기존에 빌린 우산은 정확한 PIN으로 반납할 수 있습니다.

### 학생·교직원 공통 키오스크 (v1.7)

- **별도 페이지 이동 없이** `/`에서 먼저 **우산 빌리기 / 우산 반납하기**를 선택하고, 다음 화면에서 **학생 / 교직원**을 선택합니다.
- 학생: 대여·반납 선택 → 학생 선택 → 학년·반·번호 선택 → (첫 이용 시 학생 PIN 만들기) → 공통 QR·번호 입력 → 학생 PIN → 완료
- 교직원: 대여·반납 선택 → 교직원 선택 → 교직원 ID 입력 → 공통 QR·번호 입력 → 교직원 PIN → 완료
- 교직원 ID는 대문자로 변환됩니다. QR 카메라 스캔은 HTTPS/localhost에서만 작동하고, 두 사용자 유형이 같은 카메라·입력 화면을 사용합니다.
- 과거 `/staff` 북마크는 `/`로 이동시켜 호환성을 유지합니다. **별도의 교직원용 HTML/화면은 유지하지 않습니다.**
- 교직원 1명당 **동시 대여 1개**입니다. 우산 재고는 학생과 공유하며 같은 우산을 동시에 빌릴 수 없습니다.
- 학생 월 대여 횟수/패널티 정책은 **교직원에게 적용되지 않습니다**. 교직원 대여에는 기존 관리자의 **대여 기간 설정**이 적용되고 반납 예정일이 표시됩니다.
- 관리자 재고/연체/이벤트 기록에는 대여자 `STAFF:교직원ID` 형태로 표기되어 학생(예: `6-4-16`)과 구별됩니다.
- 잘못된 PIN이 반복되면 기존 학생 PIN처럼 **5회 실패 시 15분 잠금**됩니다. 교직원 PIN은 별도 테이블에서 `scrypt` + 개별 salt로 해시 보관됩니다.
- 관리자는 직원 계정 생성·PIN 재발급·활성 변경 기록을 볼 수 있는 감사 데이터를 백업할 수 있지만, **PIN 원문이나 해시는 JSON 백업에 포함되지 않습니다.**
- 교직원 계정과 대여 기록은 개인 정보일 수 있으니 학교 내부 권한/보존 정책을 적용하세요. **실제 운영 전 교직원 신원 확인 및 관리 절차 검토는 필수**입니다.

## 대여 기한·연체 관리 (v1.5)

`/admin` → **대여 기한·연체**에서 관리자만 반납 기한과 연체 정보를 관리합니다.

1. 기본 대여 기한은 **7일**이며, 관리자가 **1~30일** 범위에서 수정할 수 있습니다. 변경값은 **새 대여부터** 적용되며 기존 대여 기한은 그대로 유지됩니다.
2. 학생이 우산을 빌리면 서버에 대여 시각과 예정일이 저장되고, 키오스크 대여 완료 화면에 **한국 시간 반납 예정일**이 표시됩니다.
3. 관리자 대여 목록에서 **대여 중/연체** 수량, 학년·반·번호, 우산 번호, 반납 예정일을 확인하고 연체만 필터링할 수 있습니다.
4. 관리자는 개별 대여 건을 **1~30일 연장**할 수 있으며 **사유(5자 이상)**를 반드시 기록합니다. 기한이 이미 지난 건은 연장 승인 시각부터 새로운 일수를 적용합니다. 원래 기한, 새 기한, 사유, 관리자 정보가 `rental_extensions` 이력에 남습니다.
5. 정상 반납 또는 관리자 분실/파손 처리 시 활성 대여가 종료됩니다. 기록은 JSON 백업에 포함됩니다.

**기존 DB 이관:** 업그레이드 시 이미 대여 중인 우산은 과거에 기한 약속이 없었으므로 **최초 업그레이드 시점부터 7일 유예**를 부여합니다. 등록된 우산 목록과 기존 대여·반납 이력은 그대로 유지하며, DB 초기화를 실행하지 마세요.

**자동 패널티·안전 알림은 추가하지 않았습니다.** 연체는 관리자 화면에서 상태로만 표시되며, 학생에게 자동 벌점을 부과하거나 대여 중인 우산의 상태를 임의 변경하지 않습니다.

관련 API: `GET/PUT /api/admin/rental-policy`, `GET /api/admin/rentals`, `POST /api/admin/rentals/{rental_id}/extend` (관리자 인증 및 변경 요청 CSRF 검사).

### 회귀 테스트

```bash
python -m pip install -r requirements.txt
python -m pip install pytest httpx
pytest -q tests/test_student_pin.py tests/test_rental_due.py tests/test_stocktake.py tests/test_staff.py tests/test_academic_year.py
```

테스트는 임시 SQLite DB에서 진행되며 실제 운영 DB를 초기화하지 않습니다.

## 월별 대여 한도와 학생별 패널티 (v0.9)

관리자 `/admin` → **학생·패널티 관리**에서 아래 기능을 사용할 수 있습니다.

- 월별 기본 대여 제한: **10회/학생**. 관리자가 1~100회로 수정 가능.
- 대여 성공 시에만 이용 횟수 1회 계산, 반납 시 횟수 복구 없음. **한국 시간(Asia/Seoul) 매월 1일 00:00**에 새 달의 기록만 계산하므로 작업 예약/DB 초기화가 필요 없음.
- 기존 `events`의 `BORROW` 기록도 해당 월 한도 계산에 포함. 한도 도달 시 새 대여 요청을 서버에서 차단하며 학생 화면에 안내.
- 관리자만 학년·반·번호별 이번 달 이용/잔여 횟수 조회 가능. 필요하면 학생에게 **그 달에만 적용되는 추가 대여 횟수**를 설정하여 긴급 대여 허용 가능.
- 학생 대여 성공 화면에는 이번 달 남은 대여 횟수를 표시.
- 패널티 점수 기본값: **분실 +3점, 과실 파손 +1점, 고의 파손 +5점, 경고 0점**.
- 우산의 분실·파손 상태 변경 자체는 패널티를 자동으로 부여하지 않음. 우산 관리에서 해당 학생을 찾아 담당 교사가 검토한 후, 사유(최소 5자) 및 사실관계 확인 체크를 거쳐 관리자만 수동 부여.
- 패널티 취소는 원본 삭제 대신 **음수 점수의 취소 기록**을 남겨 변경 이력이 추적됨. 원본 1건당 취소는 최대 1회.
- **확정된 패널티 1점당 해당 월 대여 가능 횟수 1회 차감**. 실제 한도 = max(0, 기본 월 한도 + 관리자의 추가 허용 횟수 − 해당 월 미취소 패널티 점수). 이전 달 패널티는 다음 달에 반복 차감되지 않음. 제한에 도달하면 서버에서 신규 대여를 거절하지만 기존 대여 우산의 반납은 정상 허용.
- 관리자 또는 담당 교사가 패널티를 취소하면 해당 월 차감이 복원됨(기록은 유지). 학생 사정에 따른 긴급 대여는 해당 월 추가 허용 횟수로 처리. 운영 전 학교 승인과 이의신청·정정·보존/삭제 정책 마련 필요.
- 학생 식별자는 현재 학년-반-번호(예: `6-4-16`)뿐이며 **본인 인증이 아님**. 학년도 변경 시 동일 조합이 다른 학생에게 재사용될 수 있으므로, 실제 학교 운영에서는 별도 학생 계정/학년도 구분과 기록 보존 기간 설계가 필요.

관련 API: `GET/PUT /api/admin/policy`, `GET /api/admin/student-record?student_id=...`, `PUT /api/admin/student-allowance`, `POST /api/admin/penalties`, `POST /api/admin/penalties/{id}/reverse` (모두 관리자 인증 필요, 변경 API는 CSRF 검증).

**기존 DB 파일은 삭제하지 마세요.** 서버 시작 시 새 정책/패널티 테이블이 자동 추가되며 기존 대여 기록은 유지됩니다. 다만 본 기능은 프로토타입이므로 학교 실사용 전에 정책·인증·보안 검토가 필수입니다.


### 패널티 차감 예시

기본 월 10회, 추가 허용 0회, 분실 패널티 +3점인 학생은 **해당 월 최대 7회** 대여할 수 있습니다. 이미 이번 달 7번 빌렸다면 추가 대여는 차단됩니다. 해당 패널티를 관리자가 취소하면 10회로 복원됩니다. **새달에는 이전 달의 패널티가 다시 차감되지 않습니다.**

## 실서비스 배포 후보 (v1.0) — 학교 승인 후 사용

**이 저장소는 실서비스 준비 단계이며, 실제 학교 운영 서비스가 시작된 것은 아닙니다.**
운영 전 학교의 관리자·개인정보 담당자와 학생 인증, 보유 기간, 접근 권한, 사고 대응 절차를 확정하세요.
공개 GitHub에는 실제 학생 명단, 우산 대여 기록, PIN, \`data/\` 파일 또는 백업을 올리지 마세요.

### Docker 단일 인스턴스 배포

1. 학교에서 승인한 Linux 서버, **실제 HTTPS 도메인**, TLS 역방향 프록시(Nginx/Caddy 등)를 준비합니다.
2. 프로젝트 루트에서 \`cp .env.production.example .env\`를 실행합니다. \`.env\`의 관리자 비밀번호를 안전한 임의의 20자 이상 문자열로 변경하고 \`APP_ORIGIN\`을 학교 승인 **실제 HTTPS 주소**로 바꿉니다. 해당 파일을 커밋하지 마세요.
3. \`docker compose build && docker compose up -d\`를 실행합니다. 앱은 **127.0.0.1:8000**만 열고 단일 Uvicorn worker 및 영구 Docker 볼륨을 사용합니다.
4. TLS 프록시에서 공개 HTTPS 443 요청을 앱의 로컬 8000 포트로 전달합니다. 외부에서 앱의 포트 8000을 직접 열지 마세요. 프록시는 유효한 TLS 인증서, 접근 로그의 개인정보 최소화, 신뢰 가능한 원격 주소 처리, 방화벽을 적용해야 합니다.
5. \`curl -f http://127.0.0.1:8000/healthz\`로 DB 연결 헬스체크를 확인합니다. \`/admin\` 로그인 및 실제 크롬북/키오스크의 QR 스캔·대여·반납을 **가짜 데이터**로 점검한 뒤 운영 승인을 받습니다.

운영 환경에서는 \`DEPLOYMENT_MODE=production\`, \`SECURE_COOKIES=true\`, \`APP_ORIGIN=https://정확한-도메인\`이 필수입니다. 설정이 유효하지 않으면 서버는 기동하지 않습니다.
**학생 최초 PIN 자가 등록은 운영 모드에서 차단**됩니다. 관리자가 학생의 신원을 확인한 뒤 관리자 화면에서 발급해야 합니다. 개발 모드의 자가 등록 흐름은 테스트를 위해 유지됩니다.
관리자 로그인은 사용자명당 15분간 5회, 출발지 주소당 30회 실패 시 15분 잠깁니다. 로그인 잠금 정보는 DB에 저장됩니다.

### DB 운영 백업

운영 중에도 일관된 SQLite 백업이 가능합니다.

\`\`\`bash
docker compose exec -T umbrella python backup_db.py
\`\`\`

백업은 \`/app/data/backups/umbrella-날짜.db\` 형태로 같은 영구 볼륨에 저장됩니다.
SQLite 온라인 백업 API가 커밋된 WAL 데이터를 포함해 단일 DB 스냅샷을 생성하고, \`PRAGMA integrity_check\` 확인 후 파일을 최종 확정합니다. 원본 DB는 삭제하지 않습니다.

**중요:** 같은 서버·볼륨에 백업만 남기면 서버·디스크 장애에 취약합니다.
학교 승인된 별도 암호화 저장소로 **매일 자동 복사**하고 파일 보존기간과 정기 복구 리허설을 운영 규정에 반영하세요.
백업 파일에는 학생 개인정보와 인증 해시가 있으므로 외부 공개 금지입니다.

**복구 절차:** 서비스를 완전히 종료하고 현재 DB와 WAL/SHM 파일을 별도 안전한 곳에 보존한 뒤, 정상적으로 무결성 검사된 백업 파일을 \`DATA_DIR/umbrellas.db\`로 복사합니다. 기존 WAL/SHM 잔재를 구분·정리하고 소유자/권한을 확인한 후 서버를 재시작해 관리자 화면, 현재 대여 상태를 검증합니다. 복원 이전에 발생한 기록은 유실될 수 있습니다.
\`reset_db.py\`는 테스트 초기화 도구이며 **운영 데이터에 실행하면 안 됩니다**.

### 운영 시작 전 체크리스트

- [ ] 학교 승인 및 개인정보 처리방침·보유 기간·신원 확인/발급 절차 확정
- [ ] 운영 도메인·TLS 인증서·방화벽·OS 보안 패치 및 관리자 권한 분리
- [ ] 학생/교직원 PIN 발급·회수, 5회 실패 잠금, 공용 키오스크 비밀번호 노출 테스트
- [ ] 크롬북·실제 카메라에서 QR 및 수동 입력, 연결 장애·중복 대여·반납 실기기 테스트
- [ ] 매일 오프서버 암호화 백업과 실제 데이터 복구 리허설
- [ ] 시범 운영과 오류 보고·관리 책임자 지정 후 최종 오픈 승인

주의: 코드만 롤백하고 SQLite DB 스키마가 변경되면 구버전 호환성이 깨질 수 있습니다. 배포 전 백업 후 변경하세요.
